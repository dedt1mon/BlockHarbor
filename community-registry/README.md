# Каталог сборок BlockHarbor

Лаунчер использует публичный HTTPS API `/v1` по адресу из `launcher/community_catalog.py`. `worker.mjs` обслуживает каталог, D1 (`DB`) хранит метаданные и состояние загрузок, R2 (`BUCKET`) хранит архивы. Схема базы находится в `drizzle/`.

`POST /v1/uploads` резервирует публикацию. В описании обязателен постоянный `buildKey` профиля (64 lowercase hex); он нужен для ограничения повторов и не попадает в публичный ZIP. Автор получает идентификатор сессии и секретный ключ. Он загружает части по 8 МиБ через `PUT /v1/uploads/{upload}/parts/{number}` и вызывает `POST /v1/uploads/{upload}/complete`. Публикация становится видна после проверки целостности архива. Для этих операций используется заголовок `Authorization: Bearer …`. Секрет остаётся у автора.

`GET /v1/builds` возвращает страницу опубликованных сборок. Поддерживаются параметры `q`, `category`, `version`, `loader` и `offset`. `GET /v1/builds/{id}/archive` возвращает снимок. Владелец может отозвать публикацию через `DELETE /v1/builds/{id}`. Публичный ID не даёт права на изменение или удаление.

Поиск читает только метаданные D1 и не ждёт удаления старых ZIP из R2. Просроченные публикации скрываются SQL-фильтром; физической очисткой занимаются отдельный maintenance endpoint и расписание. Если `q` содержит точный `BH-…`, старые фильтры и номер страницы не скрывают найденную запись. Лаунчер для такого запроса сразу читает `GET /v1/builds/{id}`. Этот короткий запрос подтверждает наличие и размер объекта через R2 HEAD, без повторного скачивания ZIP.

При публикации лаунчер отправляет до трёх частей одновременно, затем ждёт серверной проверки целостности и отдельно подтверждает публичную доступность записи. Владелец сохраняет квитанцию и ключ даже при потере последнего ответа; повторная проверка не создаёт второй архив. Статус публикации перепроверяется на сервере: сетевой сбой помечается как непроверенная доступность, 404/410 удаляют устаревшую локальную запись. Интерактивный GET имеет одну попытку с сетевым timeout 8 секунд; повторные попытки частей загрузки и завершения публикации сохранены.

Архив поддерживает `Range: bytes=<offset>-<end>` и `If-Range` с сильным ETag на основе SHA-256. Клиент скачивает его через общую очередь с проверкой размера/хеша и возобновлением прерванного запроса. Каждый новый запрос, включая продолжение, проверяет срок публикации. Несовпадающий `If-Range` возвращает полный HTTP 200; недопустимый диапазон — HTTP 416. Секрет владельца для скачивания не нужен.

Максимальный размер **новой** публикации — 256 МиБ (старые большие архивы остаются совместимыми с механизмом скачивания до истечения TTL). Лимит суммарного объёма можно задать числом байтов в `CATALOG_STORAGE_LIMIT`. Общий жёсткий потолок каталога — 8 ГиБ (включая незавершённые резервирования); при меньшем `CATALOG_STORAGE_LIMIT` применяется он. Незавершённая сессия истекает через 30 минут.


## Резервный публичный канал без обязательного доступа к chatgpt.site

Публичный основной реестр остаётся источником правды для публикации и удаления сборок. GitHub Actions (`.github/workflows/community-mirror.yml`) сохраняет совместимость с историческими открытыми записями **без `expiresAt`**: сверяет SHA-256 ZIP и зеркалирует их в GitHub Releases, не затрагивая секреты и закрытые загрузки. **Публикации с ограниченным сроком хранения не копируются на GitHub**, поскольку прямая ссылка на release asset не умеет прекращать доступ ровно через час. Уже зеркалированные записи с `expiresAt` удаляются из желаемого набора и снимаются при следующей успешной синхронизации. Все зеркальные релизы имеют статус *prerelease* и `latest=false`, поэтому механизм обновления лаунчера их не принимает за обновления.

- `community-mirror-index/index.json` — актуальный публичный список, формат 1, отметка времени синхронизации.
- `community-mirror-00` … `community-mirror-1f` — архивы по 32 сегментам; каждый до 1000 файлов (ограничение GitHub Releases). Сегмент вычисляется из первых двух шестнадцатеричных цифр ID по модулю 32.
- Лаунчер при недоступности основного каталога (блокировка сети, 403, 5xx) автоматически использует резервный индекс и архив. Данные ограничены сроком актуальности 2 часа; снимки проверяются по размеру и SHA-256, как и при обычном скачивании. Интерфейс явно сообщает, что зеркало содержит только старые публикации. Пустое зеркало не считается доказательством отсутствия новых сборок: клиент показывает ошибку доступности основного каталога.
- После снятия сборки с публикации зеркало удаляет архив при следующей успешной синхронизации. Уже скачанные другими пользователями копии отозвать невозможно. Синхронизация обычно выполняется каждые пять минут, но расписание GitHub Actions может сдвигаться.
- Публикация и снятие публикации по-прежнему выполняются на основном реестре, чтобы не создавать конкурирующие источники правды. Резервное зеркало предназначено для поиска и установки игроками.
- Доступность GitHub зависит от провайдера и региона. Не обещается абсолютная доступность из каждой сети.

См. `tools/sync_community_mirror.py` и тесты `tests/test_community_mirror.py`. Для принудительной синхронизации используйте `workflow_dispatch` workflow `Synchronize public BlockHarbor community mirror`.


## Публикации на 1 час

Новая политика после развёртывания обновлённого Worker: каждая проверенная публикация доступна **3600 секунд от момента подтверждённой загрузки**. По истечении срока она скрывается в списках и по ID. Фоновая очистка, отдельный maintenance endpoint и подготовка новой загрузки удаляют ZIP из R2 и запись из D1; поиск не выполняет эту работу. Новые часовые архивы остаются только на основном сервере; перед приёмкой политики необходимо выполнить обновлённую синхронизацию и проверить отсутствие прежних копий с `expiresAt` на GitHub. Установка уже скачанных копий не затрагивается, а локальные сборки пользователей не удаляются.

Лаунчер получает `expiresAt` в компактном JSON-манифесте и никогда не устанавливает просроченную запись из зеркала. Полный ZIP и его встроенный `blockharbor.json` остаются в прежнем формате, чтобы не ломать установку пользовательских модов.

**Процедура безопасного развёртывания:** [RETENTION-ONE-HOUR.md](RETENTION-ONE-HOUR.md). Для периодической очистки R2 нужен включённый Worker Cron каждую минуту либо отдельный GitHub workflow `community-cleanup.yml` на default branch. Workflow запускается по `2-57/5 * * * *` и вызывает `POST /v1/maintenance/prune`: не более восьми запросов, до 16 истёкших записей за запрос. Endpoint не принимает ID или дату, не требует секретов и имеет общий устойчивый throttle 5 секунд. Фактическое выполнение расписания нужно проверить; `wrangler.example.toml` и наличие `scheduled()` сами по себе не включают автоматизацию. Сервис сохраняет жёсткий лимит общего хранилища при параллельных публикациях.

GitHub здесь запускает очистку, а часовые ZIP хранятся в закрытом R2. Публичные `r2.dev`, прямые custom domain bucket и GitHub release assets обходили бы проверку срока. Они не должны обслуживать эти архивы. Истечение доступа точно через 3600 секунд не означает физического удаления в ту же секунду: расписание и повторы удаления могут задерживаться.

Новая миграция `0002_expiry_notifications.sql` сохраняет состояние повторов удаления и owner-only квитанции. Владелец получает уведомление через `GET /v1/publications/{id}/events` с исходным Bearer-токеном; клиент подтверждает его через `DELETE` только после записи в локальную историю. Повторная доставка не создаёт дубликатов. Квитанция подтверждает фактическое удаление, тогда как недоступность ссылки наступает по `created + 3600` независимо от задержки очистки.

Клиент не создаёт новую публикацию на сервере, который не подтвердил 3600 секунд и лимиты через `/v1/capabilities`. Скачивание и снятие существующих публикаций остаются доступны. Состояние действующего backend и ограничения проверки описаны в [аудите компонента](../docs/audits/component-sharing.md).

## Антиспам и интервал повторных публикаций

Ограничения: 256 МиБ на новую сборку, максимум 3 активных публикации с одного сетевого адреса, **три начальные попытки одной сборки, затем одна попытка в 300 секунд**. Сервер атомарно проверяет стабильный ключ профиля и дополнительный ключ идентичного архива. Повторный upload, переименование, простой, снятие публикации и перезапуск не возвращают три начальные попытки. Каталог, скачивание и продолжение начатой загрузки остаются доступны. Для новой схемы необходима миграция `drizzle/0003_build_cooldown.sql` после предыдущих миграций и стабильный серверный секрет `RATE_SALT`. Подробности и границы анонимной сетевой идентификации: [ABUSE-GUARD.md](ABUSE-GUARD.md).

HTTP 429 содержит `Retry-After`, `retryAfterSeconds` и `blockedUntil`; ожидание не продлевается отклонёнными запросами. Оно не отменяет готовые архивы или восстанавливаемые multipart-сессии. Завершённые публикации живут до своего часового срока, незавершённые — до 30 минут от резервирования.
