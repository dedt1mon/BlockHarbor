## Обнаруженные причины и исправления

| Проблема | Первопричина | Исправление |
| --- | --- | --- |
| Колокольчик не мог достоверно отражать непрочитанное после перезапуска | В SQLite не было признака прочтения | Добавлена миграция `is_read`, счётчик и API отметки прочтения |
| Новое уведомление могло быть прочитано вместе с уже открытой историей | Не было границы снимка истории | `throughId` отмечает только записи, существовавшие в прочитанном снимке |
| Задержавшийся ответ после очистки мог пометить новое сообщение | SQLite повторно использует ID после удаления всех строк | Отдельная монотонная последовательность ID сохраняется в настройках |
| Повторное серверное событие дублировалось после рестарта или очистки истории | Дедупликация сравнивала только последний текст за четыре секунды | Уникальные ключи событий в SQLite, атомарная запись между окнами |
| Владелец не узнавал об удалении публикации при закрытом приложении | Сервер удалял все сведения без сохраняемого события | Owner-only квитанция в D1, чтение по исходному ключу владельца, ACK после локальной записи |
| Потеря ответа ACK оставляла локальную очередь навсегда | Клиент повторно запрашивал уже удалённое серверное событие | Локальная отметка `notified`; повтор ACK с допустимым HTTP 404 |
| Старые публикации без `expiresAt` теряли возможность получить событие | Прежний клиент удалял ключ при публичном HTTP 404 | Миграция локального журнала владельца до удаления старой записи, проверка серверной квитанции для неизвестного старого срока |
| Один недоступный объект мешал остальной очистке | Последовательная обработка прерывалась на первом исключении | Четыре ограниченные линии удаления, durable backoff конкретной записи |
| Позднее завершение multipart могло оставить архив после снятия публикации | R2 и D1 изменялись разными операциями | Повторная проверка состояния в `finally`, удаление позднего объекта; части записываются только для активного upload |
| Два уборщика могли восстановить уже подтверждённую квитанцию | Второй использовал сохранённую копию удалённой строки | INSERT события выполняется из ещё существующей строки `builds` внутри транзакции |
| Синхронизация существующей сборки восстанавливалась лишь при обычном исключении | Собственный rollback без дискового журнала | Переиспользован `BuildCare._transaction`; журнал до первого rename, восстановление при следующем запуске |
| После аварии оставались временные скачивания синхронизации | Временная папка очищалась только `finally` | Owner marker и уборка только служебных папок завершившегося процесса |
| Обрыв скачивания сборки начинал загрузку с нуля | Отдельный потоковый транспорт обходил общую очередь загрузок | `TransferManager`, SHA-256/size, частичный кэш и `Range` с сильным ETag на сервере |
| Новый архив мог уходить на сервер без требуемого срока хранения | UI предупреждал о старой политике, API всё равно публиковал | Guard перед новой сессией/отправкой; старые скачивания и снятие публикаций сохранены |

## API уведомлений

`experienceState` содержит `notificationUnread`. `experienceNotifications` возвращает `items`, `unread`, `lastId`; каждая запись содержит `id`, `created`, `message`, `level`, `read`.

`experienceReadNotifications` принимает `{ "throughId": lastId }` и возвращает `ok`, `unread`, `lastId`. Новые записи с большими ID остаются непрочитанными. История содержит максимум 200 видимых записей. Ключи уже доставленных серверных событий сохраняются отдельно, поэтому очистка истории не вызывает их повторное появление. Секреты и личные пути по-прежнему проходят существующий redaction до записи.

`GET /v1/publications/{id}/events` требует Bearer-токен исходной публикации. Он выдаёт событие `publicationExpired` только после подтверждённого удаления R2-объекта. `DELETE` этого endpoint подтверждает доставку. Публичный ID без токена не позволяет прочитать или удалить квитанцию.

Клиент хранит ожидающие квитанции независимо от текущей видимости публикации и повторной публикации той же локальной сборки. Фоновый поток принадлежит текущему lifecycle scope, запускается не чаще одного раза в минуту, обрабатывает максимум восемь ожидающих публикаций за проход и использует сохраняемую задержку повтора до часа. UI и монитор игровых процессов не выполняют сетевой запрос в своём потоке.

## Скачивание и локальное восстановление

Установка публикации использует общую `TransferManager`: размер и SHA-256 берутся из проверенного манифеста, прерванный запрос возобновляется из ограниченного частичного кэша. Сервер поддерживает одиночный диапазон `Range`, сильный ETag на основе SHA-256 и `If-Range`; проверка истечения срока применяется также к каждому запросу продолжения. Если `If-Range` не совпадает, сервер возвращает полный архив. Некорректный диапазон получает HTTP 416. После полной проверки локального файла его импорт не зависит от дальнейшего истечения ссылки.

Резервное зеркало выбирается только после исчерпания повторов сетевого запроса или допустимого HTTP-сбоя. Отмена, неверный хеш, локальная ошибка записи, TLS-сбой и окончательный HTTP 404 не заменяются попыткой другого источника. Перед сменой источника сверяются ID, размер, SHA-256 и срок манифеста. Секрет владельца не попадает ни в URL скачивания, ни в журнал задач: архив запрашивается по публичному ID.

Временные каталоги обмена описаниями, скачивания публикаций и подготовки mrpack используют общий `launcher/staging.py`. Служебный маркер содержит идентичность процесса; восстановление удаляет только известные каталоги уже завершившегося процесса, сохраняет активные, неизвестные и перенаправленные папки. Ошибка удаления заблокированного файла оставляет каталог для следующего запуска и не мешает открытию лаунчера. Синхронизация существующей сборки проводит изменение через дисковый журнал `BuildCare`; режим `no_replace` сохраняет новый ручной файл, появившийся между проверкой и публикацией.

Независимый повторный review выявил и закрыл ещё две потери данных: ручной файл, появившийся между первым preflight и созданием журнала, и ручная замена уже опубликованного файла после аварии. Новый журнал содержит идентичность файлов и SHA-256, а для каталогов — агрегированный отпечаток всех узлов и содержимого. Подготовка отпечатка выполняется до короткой commit-блокировки. Rollback удаляет только объект с подтверждённой принадлежностью, включая проверку вложенных файлов, изменённых без изменения размера или времени самого каталога. При конфликте с прежней копией изменённый объект, исходная копия и журнал остаются на месте, а сборка получает ошибку восстановления.

Старый журнал не содержит таких доказательств. Неизвестный объект сохраняется отдельно в `recovery/preserved-*/files` с манифестом и записью истории, затем восстанавливается исходная копия. Эти сохранённые данные не попадают под автоматическую уборку. Уборка уже подтверждённого `committed` журнала повторяется независимо и не превращает успешную установку в ошибку. Проверки содержимого во время rollback завершаются даже при уже отменённом lifecycle scope.

## Срок хранения и независимая очистка

Логический срок строго равен `created + 3600`: время фиксируется при первом успешном завершении проверки ZIP и SHA-256, повторный `/complete` его не продлевает. После границы новые запросы списка, описания и архива недоступны даже при отказе уборщика.

Физическая очистка является отдельной операцией. Подготовлен `wrangler.example.toml` с минутным Cron Trigger. Вызов `scheduled()` обрабатывает до 128 записей, не более четырёх одновременно; сохранённые ошибки повторяются через 30 секунд — 1 час. `removing`, срок и задержка сохраняются в D1 и переживают рестарт. Записи `parts` и `builds` удаляются в одной D1-транзакции с созданием owner receipt после удаления R2-объекта.

Квитанции ожидают подтверждения владельца, чтобы офлайн-пользователь не потерял сообщение. Они не содержат архив, имя сборки или исходный токен. Совокупный резерв активных публикаций и квитанций ограничен 200 000; исчерпание ограничивает новые публикации вместо неограниченного роста служебных данных. Прежние ограничения 256 МиБ, 3 активные публикации на сетевую группу, 10 попыток за 10 минут, блокировка на 5 часов и общий резерв 8 ГиБ сохранены.

**Нельзя заявлять физическое удаление ровно в ту же секунду, что и истечение ссылки.** Cron, очередь, отказ R2/D1 и задержки хостинга могут отложить освобождение места. Для новых публикаций с `expiresAt` подготовленная синхронизация больше не создаёт прямые GitHub ZIP assets: такой внешний URL нельзя ограничить серверным TTL. Уже зеркалированные записи с этим полем удаляются при следующем успешном sync; legacy-публикации без срока остаются совместимыми до rollout. Клиент также проверяет `expiresAt` в сохранённом индексе. Эти изменения не запускались против production assets. Настройка native Cron не входит в документированный Sites hosting manifest и не подтверждена для действующего Site. Наличие экспортированного `scheduled()` само по себе расписание не создаёт.

Официальные документы платформы: [Cloudflare Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/), [лимиты Workers](https://developers.cloudflare.com/workers/platform/limits/), [R2 lifecycle API](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/lifecycle/). Отдельная R2 lifecycle policy для незавершённых multipart-загрузок нужна как страховка от сбоя между созданием upload и резервом D1.

- Компонентный Python-набор: **105 тестов, 105 успешно, 0 ошибок, 0 пропущено**. Включены уведомления, история/персонализация, публикации, антиспам-клиент, зеркало, обмен описаниями, ZIP-архивы и mrpack.
- Worker: **24 теста, 24 успешно, 0 ошибок, 0 пропущено**.
- Реальный отдельный процесс был принудительно завершён через `os._exit(87)` после публикации первого нового файла в существующую сборку. После перезапуска `BuildCare` восстановил исходный JAR, не оставил второй файл и удалил завершённый журнал; отдельная уборка удалила только abandoned staging.
- Проверены получение события после офлайн-периода, потеря ACK, повторная доставка, два окна, очистка истории, миграция старой базы, устаревший watermark и новые сообщения после открытия истории.
- Проверены граница TTL за 1 мс до и в момент истечения, повтор `/complete`, очистка без пользовательских запросов, отказ R2, рестарт уборщика, ограничение порции и повторный проход, гонки отзыва/complete и двух уборщиков/ACK.
- Реальный `TransferManager` в клиентском интеграционном тесте получил оборванное тело, возобновил запрос через `Range` и импортировал только полностью проверенный архив. Проверены совпадение зеркального манифеста, отсутствие токена владельца в журнале и запрет fallback при повреждении, отмене и HTTP 404. Серверные тесты проверяют Range/If-Range, ETag, неверные диапазоны и истечение ссылки при продолжении.
- Существующие проверки опасных путей, ссылок, ZIP64, размера/сжатия, SHA-256, несовпадающего манифеста, опциональных конфигураций и отдельных Store автора/получателя сохранены.
- Дополнительный набор после review восстановления: **67/67** (`test_build_care`, `test_shared_builds`, `test_catalog_batch`, `test_transaction_ownership`). Новый файл содержит восемь регрессий: создание файла в гонке, отказ уборки committed journal, same-size edit, замена inode при тех же байтах, вложенное изменение каталога после настоящего crash, обычный rollback дерева, безопасное восстановление legacy journal и rollback при отменённом scope.

## Что осталось до готовности серверной функции

1. Проверить и одобрить публикацию подготовленного кода действующего Site. До этого `/v1/capabilities` остаётся 404 и новые клиентские публикации намеренно блокируются.
2. Применить новые миграции к прежней D1 с резервной копией, сохранить `RATE_SALT` как runtime secret, сохранить прежние DB/R2 и аудиторию.
3. Настроить и подтвердить работающий независимый scheduler и дополнительную R2 lifecycle policy. Проверить фактические время удаления, очередь и занимаемые байты на действующем хостинге.
4. Провести разрешённую публикацию тестовой сборки на двух реальных клиентских установках, проверить скачивание до срока, отказ после срока, R2/D1 очистку, доставку offline receipt и удаление зеркального asset.

До этих действий серверный раздел ТЗ не считается полностью принятым. Локальные тесты и подготовленный код не подменяют результат production-проверки.
