# Обновления и загрузки BlockHarbor 2.1

## Пользовательский сценарий

Во вкладке **Настройки → Загрузки и обновления** можно выбрать стабильный или тестовый канал, проверить
релизы, прочитать описание и скачать установщик. Загрузка не закрывает Minecraft.
После проверки файла кнопка установки позволяет дождаться окончания игры и
текущих операций. Перед установкой нужно закрыть остальные окна BlockHarbor.
Затем BlockHarbor закрывает своё окно и передаёт управление
обычному установщику Windows.

Перед обновлением сохраняются предыдущий `BlockHarbor.exe` и согласованная копия
SQLite с настройками лаунчера. Если опубликован установщик текущей версии, он тоже
кэшируется для возврата. Кнопка возврата появляется только для сохранённой версии
с совместимым форматом данных. Она возвращает приложение; миры и изменения
содержимого сборок не откатываются. Для них предусмотрены отдельные точки
восстановления и копии миров.

Незавершённая установка после аварийного закрытия не возобновляется самопроизвольно:
пользователь снова нажимает кнопку установки. Игровые процессы не завершаются
принудительно.

## Проверка источника

Источник релизов фиксирован: `dedt1mon/BlockHarbor` на GitHub. Начальный адрес
каждого файла должен в точности совпадать с путём выбранного релиза в этом
репозитории. Разрешены HTTPS и необходимые домены доставки GitHub; переходы на
другие домены отклоняются. SHA-256 берётся из метаданных GitHub release asset или
из `SHA256SUMS.txt` того же релиза. Проверяются объявленный размер и фактический
хеш. Повреждённый файл не запускается.

Это модель доверия к HTTPS и аккаунту репозитория. Она не заменяет подпись
издателя Authenticode и не защищает от захвата аккаунта владельца репозитория.
Сейчас установщик не имеет Authenticode-подписи.

Все релизы начиная с 2.0 должны включать файл `BlockHarbor-update.json`:

```json
{
  "format": 1,
  "version": "2.1.0",
  "dataSchema": 1,
  "minDataSchema": 1,
  "maxDataSchema": 1,
  "rollbackSafe": true
}
```

Его можно сформировать командой:

```bash
python tools/release_update_manifest.py --version 2.1.0 --output ../release/BlockHarbor-update.json
```

При изменении схемы данных значения необходимо пересмотреть. Несовместимые или
неописанные схемы блокируют автоматическую установку. Нельзя выставлять
`rollbackSafe: true`, если новая версия проводит необратимую миграцию данных.

## Центр загрузок

`TransferManager` предоставляет два сетевых слота и очередь с ограничением на 24
ожидающих/работающих файла. Состояние включает реальные принятые байты, известный
размер, среднюю скорость текущей попытки и этап проверки. Для операций, которые
сообщают только стадию подготовки, интерфейс не показывает выдуманный процент.

Перед публикацией файла проверяются все контрольные суммы, полученные от
каталога. Рабочий файл заменяется атомарно только после успешной проверки.
Частичные данные лежат отдельно в `download-cache`. Продолжение использует
`Range` и `If-Range` при наличии сильного ETag или Last-Modified. Ответ 206 должен
содержать правильный Content-Range; при ответе 200 загрузка начинается сначала.
Итоговые хеши всегда проверяются заново.

Отменённую фоновую загрузку установщика можно повторить из центра. Для модов и
паков повторяется исходная операция установки, чтобы заново проверить план и
состояние сборки. Совпадающая частичная загрузка может быть использована повторно
даже при новом временном каталоге: должны совпасть URL, все хеши и размер.

История содержит до 100 задач. Очистка истории удаляет их частичные данные, но
не удаляет уже установленные файлы. Активные задачи не очищаются. Прерванная при
закрытии приложения задача помечается как прерванная; постоянные фоновые задачи
можно повторить после нового запуска.

## Передача управления установщику

Отдельный `update_helper.py` открывает Windows process handles основного Python
процесса и нативного загрузчика **до** подтверждения готовности. Это не позволяет
перепутать завершившийся процесс с позднее переиспользованным PID. Помощник
дожидается обоих завершений, повторно проверяет SHA-256 и запускает установщик
без командной оболочки и без повышения прав. У самого установщика сохраняется
проверка занятых файлов и активных сессий.

Bootstrap передаёт свои путь и PID через `BLOCKHARBOR_LAUNCHER_EXE` и
`BLOCKHARBOR_BOOTSTRAP_PID`. Пока выполняется подготовка/передача управления,
главное приложение не должно начинать новые операции изменения файлов.

## Идентичность окна в Windows

У проверенного окна лаунчера задаются документированные Shell-свойства
AppUserModelID, команда повторного запуска, название и иконка. Команда запуска
ведёт на `BlockHarbor.exe`, а не на внутренний браузер с истёкшим локальным URL.
Свойства задаются только после проверки одноразовой метки окна. Существующие
ярлыки помечаются тем же AppUserModelID только после проверки их целевого файла;
аргументы ярлыков сборок сохраняются. Закрепление остаётся действием пользователя.

## Проверка

Модульные тесты проверяют ограничения источников и путей, сохранность старого
файла при ошибке хеша, продолжение диапазона, отмену, восстановление задач после
перезапуска, каналы релизов, совместимость данных и порядок передачи управления.
Нативные Win32-вызовы требуют отдельной проверки на Windows. Linux-тесты порядка
вызовов не заменяют запуск установщика, Edge и Steam на реальной машине.
