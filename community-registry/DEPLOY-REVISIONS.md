# Применение обновлений к уже опубликованным сборкам

Публикации до обновления остаются в D1/R2, с теми же ID и ключами владельца. Для активации автообновления клиентского лаунчера **необходимо обновить сервер по прежнему адресу**, не создавая новый каталог и не сбрасывая базу.

1. Сделайте резервную копию существующей базы D1 и запомните привязки `DB`, `BUCKET` и текущий публичный домен.
2. Примените **только новую миграцию** `community-registry/drizzle/0001_revisions.sql` к той же D1. Миграция добавляет ключ активного ZIP, записи незавершённых обновлений и отложенную очистку старых снимков. Применять её повторно не нужно.
3. Разверните новую версию `community-registry/worker.mjs` с прежними привязками D1/R2 и **тем же доменом**, который указан в `launcher/community_catalog.py`. Не заменяйте всю базу и хранилище на пустые.
4. Проверьте `GET /`: должен возвращаться `"schema":2` и `"capabilities":["revisions"]`. Также проверьте, что `GET /v1/builds` по-прежнему содержит старые публикации.
5. Запустите тесты `node --test community-registry/worker.test.mjs` и `python -m unittest discover -s tests -p 'test_community*.py' -q`. В тестовой публикации проверьте `POST /v1/builds/{id}/revisions`, последовательность PUT-частей и `POST /v1/revisions/{upload}/complete`: ID должен сохраниться, SHA-256 поменяться; старая копия должна остаться доступной при неудаче.
6. После подтверждения живого сервера можно публиковать новую стабильную версию лаунчера. Изменения дополняемых файлов будут проверяться с задержкой; не требуется повторная ручная публикация. Зеркало GitHub Releases подхватит обновление при очередной синхронизации.

Протокол обновления использует уже имеющийся **секретный токен владельца**. Для чужого токена запись возвращает HTTP 403. Клиент не передаёт и не сохраняет новые секреты на сервере. Снимки загружаются отдельно, проверяются, затем атомарно переключается ссылка на новый ZIP; предыдущий объект удаляется с задержкой для завершения уже начатых скачиваний.

**Важно:** один только коммит в GitHub или выпуск нового установщика не обновляет развернутый Worker. Пока `GET /` живого сервера не содержит `capabilities: ["revisions"]`, автообновления на сервере не поддерживаются.
