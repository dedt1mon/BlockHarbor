# Ограничение повторных публикаций BlockHarbor

## Действующая схема протокола

| Ограничение | Значение |
| --- | --- |
| Размер одного нового публичного ZIP | **256 МиБ** (268 435 456 байт) |
| Активные сборки с одного сетевого адреса | **3**, включая незавершённые загрузки |
| Начальные попытки публикации одной сборки | **3 без обязательного интервала** |
| Каждая следующая попытка этой сборки | **Не раньше чем через 300 секунд после предыдущей принятой попытки** |
| Общий резерв архивов | **Не более 8 ГиБ**, либо меньший `CATALOG_STORAGE_LIMIT` |
| Доступность готовой публикации | **3600 секунд после успешной проверки ZIP и SHA-256** |
| Незавершённая загрузка | **30 минут** |
| Устойчивые ключи ограничения | **Не более 200 000**; новая пара не принимается при исчерпании места |

Прежняя схема «10 попыток за 10 минут, затем запрет на пять часов» заменена. Ограничивается создание новой сессии через `POST /v1/uploads`; скачивание, снятие своей публикации, повтор части и завершение уже начатой загрузки продолжают работать. Ограничение не отменяет готовые публикации и не обрывает восстанавливаемые загрузки.

### Точный счётчик

Третья принятая попытка задаёт `next_allowed = server_now + 300`. Запрос до этой границы получает HTTP 429, `Retry-After`, `retryAfterSeconds` и `blockedUntil`. В точности на границе разрешена одна попытка; она снова устанавливает интервал 300 секунд. Отклонённые повторы не сдвигают границу. Простой, перезапуск сервера или лаунчера, удаление публикации и повтор `/complete` не возвращают три начальные попытки.

Попытка считается после проверки описания и идентификаторов, но **до** выделения R2 multipart и проверки свободных слотов: отказ по занятому хранилищу тоже не позволяет бесконечно нагружать резервирование. Уже действующая неизменённая публикация может быть возвращена из клиентского состояния без новой сессии; это не продлевает её TTL.

В JSON ошибки сохранён технический код `PUBLISH_RATE_BAN` для существующего клиентского обработчика. Это не пятичасовая блокировка: новая политика возвращает ожидание не более 300 секунд и сообщение об интервале для этой сборки.

## Идентификация сборки и приватность

`POST /v1/uploads` требует поле `buildKey`: 64 шестнадцатеричных символа в нижнем регистре. Лаунчер выводит его из постоянного UUID локального профиля. Переименование, изменение состава, новая сессия загрузки и перезапуск лаунчера его не меняют. Поле не включается в публичный ZIP или каталог; сервер хранит только производный digest.

Сервер проверяет два ключа одновременно:

1. Сетевой издатель + постоянный `buildKey`: изменение имени и файлов той же локальной сборки не восстанавливает burst.
2. Сетевой издатель + SHA-256 архива: смена `buildKey` для идентичного содержимого не обходит его счётчик.

Один SQLite `INSERT … ON CONFLICT … RETURNING` с материализованным условием допуска изменяет оба счётчика атомарно либо не изменяет ни один. Счётчики хранятся в D1 `publication_rate`; уборщик архивов их не удаляет. При исчерпании лимита служебных ключей сервер возвращает 503 для новой пары вместо незаметного сброса защиты. Существующие ключи могут продолжать использоваться в пределах своей квоты.

Издатель определяется по доверенному `CF-Connecting-IP` на входе платформы. Worker вычисляет HMAC-SHA-256 с секретным `RATE_SALT`; исходный IP и локальный UUID не сохраняются в D1 и намеренно не логируются. `RATE_SALT` должен оставаться стабильным между развёртываниями: его административная замена меняет анонимизированные ключи и, соответственно, начинает новые счётчики.

Это защита анонимного сервиса, а не аутентифицированный аккаунт владельца. Разные сборки за одним NAT имеют отдельные основные счётчики, но идентичные архивы и лимит трёх активных резервирований могут разделять квоту. Смена IP/VPN либо одновременно нового профиля и содержимого не позволяет гарантированно определить того же человека. Проверка двух независимых сетей и доверенного источника IP остаётся эксплуатационной проверкой; общий адрес промежуточного proxy нельзя выдавать за индивидуальный адрес пользователя. Для защиты от распределённого потока нужны средства платформы, а не обещание абсолютной защиты этим API.

## Контракт готовности

`GET /v1/capabilities` возвращает:

```json
{
  "publicRetentionSeconds": 3600,
  "manifestFormat": 1,
  "ownerNotificationFormat": 1,
  "publishLimits": {
    "maxArchiveBytes": 268435456,
    "maxActive": 3,
    "burstAttempts": 3,
    "cooldownSeconds": 300,
    "rateScope": "publisher-build",
    "stableBuildKeyRequired": true
  }
}
```

Endpoint проверяет наличие D1/R2 bindings, секрета и новой схемы. Он не проверяет настройки публичного доступа bucket или фактическое выполнение внешнего расписания: их нужно подтвердить отдельно. При старом либо неподтверждённом контракте клиент запрещает новую публикацию, сохраняя чтение и снятие существующих.

## Развёртывание и проверка

1. Сохранить существующие `DB`, `BUCKET`, URL и данные. Уже применённую `0000_catalog.sql` не менять и не запускать заново.
2. Применить только отсутствующие миграции `0001_abuse_guard`, `0002_expiry_notifications`, `0003_build_cooldown` через журнал `drizzle/meta/_journal.json`. `0001` остаётся исторической миграцией; новый Worker использует таблицы из `0003`. Не переписывать историю применённых миграций.
3. Установить случайный серверный секрет `RATE_SALT` длиной не менее 32 символов. Не включать его в исходники, конфигурацию клиента, workflow или сообщения. При существующем корректном секрете сохранить его.
4. Развернуть Worker и проверить `/v1/capabilities`. Убедиться, что архивы доступны только через проверяющий TTL `/v1/builds/{id}/archive`, без открытого `r2.dev` или обходного custom domain.
5. Включить настоящий Worker Cron `* * * * *` либо отдельный GitHub workflow `community-cleanup.yml` на **default branch**. GitHub вызывает только публичный, ограниченный endpoint очистки; пользовательские и административные ключи не требуются. Подробности в [RETENTION-ONE-HOUR.md](RETENTION-ONE-HOUR.md).
6. Выполнить целевые проверки: `node --test community-registry/worker.test.mjs` и `python -m unittest discover -s tests -p 'test_community*.py' -q`. Тесты используют настоящий SQLite и производственные exporter/API, включая границу 300 секунд, параллельные запросы, перезапуск, два ключа и сохранение действующих архивов при очистке.
7. На живом сервере создать только отдельную маленькую тестовую публикацию, сверить скачанный SHA-256 и `expiresAt`, снять её исходным owner-токеном и проверить 404. Отдельно подтвердить успешный запуск расписания и мониторинг отложенных удалений. Локальные тесты не доказывают эти настройки действующей платформы.
