# Защита публикаций BlockHarbor от спама

## Ограничения (действуют только на POST /v1/uploads)

| Ограничение | Значение |
| --- | --- |
| Размер одного нового публичного ZIP | **256 МиБ** (268 435 456 байт) |
| Активные сборки с одного адреса сети | **3** (включая незавершённые загрузки) |
| Попытки запуска публикации | **10 за 10 минут** |
| 11-я попытка внутри окна | **HTTP 429, запрет публикаций на 5 часов** |
| Общий объём зарезервированных и опубликованных ZIP | **не более 8 ГиБ**, либо меньший `CATALOG_STORAGE_LIMIT` |
| Время жизни готовой сборки | **1 час после подтверждения SHA-256** |

Ограничение размера проверяется до выделения R2 multipart upload. Предел активных сборок проверяется в атомарном запросе на резервирование D1. Попытки считаются по времени первой попытки в 10-минутном окне; счётчик записывается **атомарным SQLite UPSERT**. Если за окно было сделано 10 попыток, на 11-й начинается блокировка на пять часов. Даже запросы, которым отказано из-за занятых слотов, учитываются, чтобы пользователь не мог бесконечно нагружать сервер. Повторные запросы во время блокировки не продлевают её. В момент блокировки сервер отменяет ещё незавершённые multipart-загрузки из той же группы, освобождая зарезервированное место. Уже успешно опубликованные архивы не затрагиваются.

**Блокируется только создание новых публикаций.** Чтение каталога, скачивание, удаление своих публикаций и остальные функции лаунчера продолжают работать. Уже опубликованные сборки не удаляются из-за одного превышения лимита; они автоматически исчезнут по TTL. Неверный пароль/токен для чужой публикации по-прежнему не даёт прав на её удаление.

## Приватность и ограничения анонимной защиты

Незавершённая сессия резервирования истекает через **30 минут**, после чего фоновая очистка освобождает объект и резерв места.

Сервер использует `CF-Connecting-IP` как best-effort сетевой идентификатор, вычисляет **HMAC-SHA-256 с секретным `RATE_SALT`** и сохраняет в D1 только результат. Исходный IP в D1 не пишется, в коде намеренно не логируется. Секрет хранится **только в настройках Worker**, не в GitHub и не в клиентском EXE.

Без учётных записей невозможно гарантированно отличить людей за одним NAT, корпоративным прокси или CGNAT; такие игроки могут разделить квоту. Смена VPN/IP может обойти ограничение. Если сервис работает за другим Worker/proxy, `CF-Connecting-IP` может обозначать IP прокси, а не игрока. **Перед релизом обязательно проверить два независимых пользовательских подключения.** Если оба имеют одинаковый идентификатор в backend, нельзя применять per-IP блокировку до настройки доверенного источника адресов либо дополнительного механизма авторизации/проверки; общий IP может заблокировать невиновных пользователей.

По завершении срока хранения счетчик удаляется из D1 через `scheduled()`; это предотвращает бесконечный рост базы. Нельзя обещать абсолютную защиту от масштабной DDoS/бот-атаки только правилами приложения; для этого используется сетевой антибот/фаервол на уровне платформы.

## Необходимая настройка живого Worker

1. Сохранить резервную копию текущей D1 и настройки R2, `DB`, `BUCKET`; не создавать пустые базы взамен существующих.
2. Применить **только миграцию** `community-registry/drizzle/0001_abuse_guard.sql` к существующей D1 (добавляет таблицу `publisher_rate` и индекс; старые публикации не меняет). Например, при настроенном Wrangler: `wrangler d1 execute <DB_NAME> --remote --file=community-registry/drizzle/0001_abuse_guard.sql`.
3. Сгенерировать случайный секрет длиной не менее 32 символов и сохранить его как секрет Worker **`RATE_SALT`**, например через интерфейс Cloudflare / команду `wrangler secret put RATE_SALT`; никогда не публиковать его в исходниках или в чате.
4. Развернуть обновлённый `community-registry/worker.mjs` в том же Worker/окружении, где уже работает каталог. Оставить Cron Trigger `*/5 * * * *`.
5. Проверить `GET /`: в `publishLimits` должны быть видны `maxArchiveBytes:268435456`, `maxActive:3`, `windowSeconds:600`, `maxAttempts:10`, `banSeconds:18000`.
6. Выполнить интеграционные тесты с **двух независимых сетей**: проверить, что IP различаются (через анонимизированные HMAC), лимит активных сборок, 11-й запрос/HTTP 429/`Retry-After`, корректное закрытие модального окна, доступность скачивания и существующих функций, окончание блокировки.
7. Сверить занятие R2 (лимит защищает только архивы BlockHarbor, учтённые в D1; чужие объекты в том же bucket требуют отдельного мониторинга). При превышении лимита сервис запрещает новые публикации без платной операции резервирования.
8. Только после успешного развёртывания и проверки можно включать защищённый клиент в стабильный релиз.

Новых фоновых серверов, VPS, P2P и клиентских ключей администратора не требуется. **Без применения миграции и настройки `RATE_SALT` новый Worker намеренно не принимает публикации** — это безопаснее, чем тихо выключить антиспам.
